# SentinelOps Audit Architecture & Security Event Monitoring

## 1. Overview & Trust Boundaries

SentinelOps provides an append-only, tenant-isolated audit trail designed to record security-sensitive events, administrative operations, incident triage activities, and digital forensic evidence actions.

### Important Trust Boundary Clarification:
Application-level append-only behavior is **not equivalent to absolute cryptographic immutability**. 
- Application-level protections guarantee that authenticated callers (including `SUPER_ADMIN` and `TENANT_ADMIN`) cannot alter, patch, or delete audit records through any API endpoint.
- Database administrators with direct `psql` root access or hypervisor/cloud infrastructure operators could alter database rows directly unless independent external checkpointing is in place (e.g., write-once-read-many (WORM) storage, append-only cold object locks, or remote SIEM forwarding).
- SentinelOps implements per-tenant **SHA-256 cryptographic hash chaining** so that database-level tampering, retro-active log alteration, or record deletion is readily detected by the verification engine (`/api/v1/audit-events/verify-chain`).

---

## 2. Event Schema & Canonical Serialization

Each `AuditEvent` captures:
- `id`: UUID primary key.
- `tenant_id`: Foreign key to `tenants.id` (nullable only for system/anonymous actions).
- `actor_user_id`: UUID of the authenticated actor (`users.id`).
- `actor_type`: `USER`, `SYSTEM`, or `ANONYMOUS`.
- `action`: Stable uppercase identifier (e.g., `LOGIN_SUCCESS`, `INCIDENT_CREATED`, `EVIDENCE_UPLOADED`).
- `resource_type`: Affected entity type (`user`, `incident`, `incident_note`, `evidence`, `tenant`).
- `resource_id`: String identifier of the target resource.
- `outcome`: `SUCCESS`, `FAILURE`, or `DENIED`.
- `occurred_at`: Server-generated UTC timestamp.
- `request_id`: Request correlation ID extracted from `X-Request-ID` or generated by the server.
- `source_ip`: Client IP address extracted safely from `X-Forwarded-For` or connection socket.
- `user_agent`: Sanitized, truncated browser/client user agent string (max 512 chars).
- `details`: Non-sensitive JSON metadata payload with automatic secret redaction.
- `previous_hash`: SHA-256 hash of the preceding event in the tenant's chain (or genesis hash).
- `event_hash`: SHA-256 hash of the canonically serialized event data.

### Canonical Serialization
To guarantee reproducible hashes across architectures, canonical JSON is serialized with sorted keys and compact separators:
```json
{
  "action": "...",
  "actor_type": "...",
  "actor_user_id": "...",
  "details": {...},
  "id": "...",
  "occurred_at": "...",
  "outcome": "...",
  "previous_hash": "...",
  "resource_id": "...",
  "resource_type": "...",
  "tenant_id": "..."
}
```

## 3. Recorded Action Categories

1. **Authentication & Identity**:
   - `TENANT_REGISTERED`
   - `LOGIN_SUCCESS`
   - `LOGIN_FAILED`
   - `LOGIN_DENIED` (e.g. inactive account or deactivated tenant)
   - `LOGOUT`
   - `CHANGE_PASSWORD_SUCCESS`
   - `CHANGE_PASSWORD_FAILED`
2. **User & Tenant Administration**:
   - `USER_CREATED`
   - `USER_UPDATED` (role changes, active status toggles)
   - `PRIVILEGE_ESCALATION_ATTEMPT` (recorded as `DENIED`)
3. **Incident Management & Investigation**:
   - `INCIDENT_CREATED`
   - `INCIDENT_UPDATED` (status transitions, severity changes, analyst assignments)
   - `INVESTIGATION_NOTE_ADDED`
4. **Digital Evidence & Forensics**:
   - `EVIDENCE_UPLOADED`
   - `EVIDENCE_UPLOAD_DENIED`
   - `EVIDENCE_VALIDATION_FAILED` (disallowed formats, malware PE/ELF signatures)
   - `EVIDENCE_DOWNLOADED`
   - `CROSS_TENANT_ACCESS_DENIED` (Anti-IDOR security event)

---

## 4. Privacy & Secret Redaction Policy

Audit details are processed by `sanitize_audit_details(...)` prior to database persistence:
- Any keys matching sensitive patterns (`password`, `token`, `secret`, `authorization`, `cookie`, `file_content`, `raw_body`) are strictly replaced with `[REDACTED]`.
- Plaintext passwords or JWT access tokens are never recorded in database logs.
- String fields are truncated to prevent log exhaustion attacks.

---

## 5. Audit Verification & Tampering Detection

Tenants and administrators can verify their audit trail integrity on-demand:
- Walk the tenant's event sequence ordered by `occurred_at ASC, id ASC`.
- Verify each event's `previous_hash` matches the predecessor's `event_hash`.
- Re-compute each event's canonical SHA-256 digest and verify match against `event_hash`.
- Any modified column, deleted row, or reordered sequence causes verification to return `is_valid: false` with the exact `broken_event_id`.

---

## 6. Failure Modes & Operational Guidance

1. **Transactional Consistency**:
   - Critical operations and their audit events are committed in the same database transaction. If the transaction rolls back, no misleading audit record is created.
   - For security failures (such as `LOGIN_FAILED`, `PRIVILEGE_ESCALATION_ATTEMPT`, or `CROSS_TENANT_ACCESS_DENIED`), audit records are committed to ensure security monitoring visibility even when the main request aborts.
2. **External SIEM Integration**:
   - For enterprise compliance (SOC 2, ISO 27001), forward audit logs to an external append-only log aggregator (e.g. Splunk, Datadog, AWS CloudWatch Logs with Object Lock).
